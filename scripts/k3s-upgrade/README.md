# k3s upgrade

`k3s-upgrade.sh` upgrades the single-node k3s cluster to a given version and backs up the
datastore first, so every step can be rolled back.

## How a k3s upgrade works

k3s is a Kubernetes distribution shipped as a single binary (`/usr/local/bin/k3s`) that bundles
the API server, scheduler, controller manager, kubelet, kube-proxy, containerd and flannel.
Upgrading k3s therefore upgrades Kubernetes. A version like `v1.35.10+k3s1` means Kubernetes
`1.35.10`, k3s release `1` for that version.

The official installer (`get.k3s.io`) replaces the binary, regenerates the systemd unit from the
flags it is given and restarts the service. Running pods keep running during the restart; only
the API is unavailable for a short time. After startup k3s also updates its bundled add-ons
(CoreDNS, metrics-server, local-path-provisioner).

Not upgraded by k3s: Flux, Helm releases, applications, the OS and `kubectl` on the workstation.

Rules:

- **One minor version at a time** (`1.34 → 1.35 → 1.36`); skipping minors is not supported.
- **Keep the install flags.** The installer rewrites the systemd unit, so a missing flag is lost.
  This cluster runs with `--disable-helm-controller`: Helm releases are managed by Flux, and
  without the flag k3s would deploy its bundled Traefik next to the one already installed.
- **No in-place downgrade.** The datastore may be migrated, so rollback means restoring the
  backup taken before the step.

## What the script does

1. Validates the target version and refuses a downgrade or a skipped minor version.
2. Stops k3s and copies the SQLite datastore (`server/db`), the server token and the current
   binary to `/root/k3s-backup-<current version>/`.
3. Runs the installer with the target version and the cluster's flags.
4. Waits until the node is `Ready`. If the install fails, it starts k3s again.

## Procedure

Before upgrading:

```bash
# Removed APIs in the target version (should report nothing)
pluto detect-all-in-cluster --target-versions k8s=v1.37.0 -o wide
# Supported Kubernetes range of each Helm chart
helm show chart <repo>/<chart> --version <version> | grep kubeVersion
```

Also read the k3s release notes for the target version1
(<https://github.com/k3s-io/k3s/releases>). Available versions are listed by channel at
<https://update.k3s.io/v1-release/channels>.

Upgrade (from the repository root on the workstation):

```bash
scp scripts/k3s-upgrade/k3s-upgrade.sh homelab:~
ssh -t homelab sudo ./k3s-upgrade.sh v1.35.10+k3s1
```

Verify:

```bash
kubectl get nodes -o wide                            # new version, Ready
kubectl get pods -A | grep -vE 'Running|Completed'   # empty
flux get all -A --status-selector ready=false        # empty
```

Repeat for the next minor version. Remove old `/root/k3s-backup-*` directories once the cluster
has been stable for a few days.

## Rollback

On the node, using the backup taken before the failed step:

```bash
B=/root/k3s-backup-<previous version>
sudo systemctl stop k3s
sudo rm -rf /var/lib/rancher/k3s/server/db
sudo cp -a $B/db /var/lib/rancher/k3s/server/
sudo cp -a $B/token /var/lib/rancher/k3s/server/token
sudo cp -a $B/k3s-binary /usr/local/bin/k3s
sudo systemctl start k3s
```

The binary restore keeps the systemd unit generated by the newer installer; the flags are the
same, so this is fine.
